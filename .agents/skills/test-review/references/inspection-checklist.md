# テスト・インスペクションチェックリスト

テストコードを追加・変更したとき、またはテスト不足を調査するときに使用する。全項目を機械的に満たすのではなく、各分類を「適合」「指摘あり」「対象外」で判定し、対象外には短い理由を付ける。

## 1. 仕様との対応

- 要求と完了条件に対応するテストが特定できる。
- 正常系、重要な異常系、境界値から必要なケースが選ばれている。
- 未実装の将来仕様を現在の合格条件にしていない。
- バグ修正では、可能な限り修正前に失敗する再現ケースがある。

## 2. テストレベル

- UT・IT・STのどこで保証するかが結合範囲に合っている。
- 同じ振る舞いを複数レベルで無目的に重複検証していない。
- STが内部ロジックの全組み合わせを背負っていない。
- 重要な利用者導線や環境境界が、UTだけで済まされていない。

## 3. assertion

- テスト名とassertionが同じ振る舞いを検証している。
- 「表示された」「成功した」だけでなく、重要な結果を具体的に検証している。
- false positiveを生む曖昧な部分一致や過度に広い条件がない。
- 実装コードと同じ計算をテスト側で再実装していない。

## 4. 分離と実在性

- mockは外部境界など必要な箇所に限定されている。
- mockのデータと応答が実際の契約に沿っている。
- ITでは検証対象の連携をmockで分断していない。
- STでは利用者と同じ公開入口から操作している。

## 5. 安定性

- テスト同士で状態や実行順序を共有していない。
- 時刻、乱数、ネットワーク、外部サービスへの依存が制御されている。
- 非同期処理を固定時間の待機だけで同期していない。
- 再試行によって恒常的な不具合を隠していない。

## 6. 保守性と実行性

- テスト名から前提・操作・期待結果を理解できる。
- 準備処理の重複と共通化がどちらも過剰でない。
- ローカルおよび必要なCIで実行できるコマンドが明確である。
- 失敗時に原因となったテストレベルと振る舞いを特定できる。
- テストを無効化したり、assertionを弱めたりして合格させていない。

## 7. 結果の記録

- 実行したコマンドと成功・失敗・未実行を区別している。
- 未実行項目には理由と残るリスクがある。
- 指摘は「不足テスト」と「テストコードの品質問題」に分かれている。
- 指摘ごとに重要度、対象箇所、発生条件、期待する修正がある。
