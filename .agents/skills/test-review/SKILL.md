# テストレビュー

テストコードが本当に仕様を守れているかを評価するための手順です。

## レビュー準備

1. `AGENTS.md`、関連する仕様、存在する場合は [`docs/development/testing-strategy.md`](../../../docs/development/testing-strategy.md) を読む。
2. テスト対象の本番コードを読む。
3. テストが何を保証しようとしているか整理する。
4. 既存のテスト構成と慣習を確認する。
5. `references/inspection-checklist.md` を使ってインスペクションを実施する。

## レビュー観点

### 仕様カバレッジ

- 重要な正常系があるか。
- 重要な異常系があるか。
- 境界値が必要なのに欠けていないか。
- バグ修正なら再発防止テストになっているか。

### assertion

- assertionが弱すぎないか。
- 「例外が出ない」だけで済ませていないか。
- false positiveになり得ないか。
- 期待値が仕様ではなく現在実装の偶然に依存していないか。

### mock・stub

- 過剰なmockで本来の統合関係を隠していないか。
- mockの返り値が実際の契約と乖離していないか。
- 外部境界ではなく内部実装を細かくmockしていないか。

### 安定性

- 時刻、乱数、ネットワーク、並列実行に無制御で依存していないか。
- テスト間で状態を共有していないか。
- 実行順序に依存していないか。

### 保守性

- 同じ準備コードが過剰に重複していないか。
- テスト名から意図を理解できるか。
- 1つのテストに複数の無関係な責務がないか。

## 出力

指摘は次の2種類に分ける。

1. 不足しているテスト
2. 既存テスト自体の品質問題

追加テストを提案するときは、入力・条件・期待結果まで具体化する。
単にテスト数やカバレッジ率を増やすことを目的にしない。

レビュー結果には、チェックリストの各分類について「適合」「指摘あり」「対象外」を記録する。指摘には重要度、対象箇所、問題になる条件、期待する修正を含める。
