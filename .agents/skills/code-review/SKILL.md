# コードレビュー

実装差分を、正しさと保守性を中心にレビューするための標準手順です。

## 準備

1. `AGENTS.md` を確認する。
2. タスクの目的と完了条件を確認する。
3. 関連する `docs/` を読む。
4. 差分だけでなく、呼び出し元・呼び出し先・テストも読む。

## レビュー順序

### 1. 仕様

- 要求を満たしているか。
- 勝手な仕様追加・変更がないか。
- docsと矛盾していないか。
- Issueまたはタスクの受け入れ条件を満たしているか。

### 2. 正しさ

- ロジック上の誤りがないか。
- 条件分岐の抜けがないか。
- NULL、空値、境界値を扱えているか。
- 非同期処理やエラー経路に問題がないか。

### 3. 回帰

- 既存の呼び出し側を壊していないか。
- API、DB、型、外部契約を破壊していないか。

### 4. 保守性

- 不要な抽象化や複雑化がないか。
- 重複実装がないか。
- 既存パターンから理由なく逸脱していないか。
- ファイルや関数が、独立した複数の変更理由を持っていないか。
- UI、domain logic、I/O、永続化など異なる責務が不自然に混在していないか。
- 分割されたmoduleが具体的な責務名と一方向の依存を持つか。
- 分割不足だけでなく、過剰な委譲、細分化、interface、曖昧なutilsがないか。

保守性を深掘りする場合は `modularity` と `coding-standards` を確認し、必要に応じて `maintainability_reviewer` に独立監査を依頼する。

### 5. テスト

- 変更に対応するテストがあるか。
- 重要な異常系が欠けていないか。
- テストが実際の仕様を検証しているか。

### 6. ドキュメント

- DB、API、AI、開発手順などの変更にdocs更新が必要ではないか。
- 外部データの追加・変更・削除では、関連docs、ライセンス、帰属表示、実装が一致しているか。
- 長期的な技術判断の変更にADRが必要ではないか。
- デプロイ、監視、migration、rollbackの変更が運用文書へ反映されているか。

### 7. 依存関係とライセンス

`package.json` やlockfileに差分がある場合は `dependency-management` Skillの確認結果をレビューする。

- 追加・更新・削除された直接依存とtransitive dependencyが特定されているか。
- ライセンスを一次情報で確認し、runtimeと開発時依存を区別しているか。
- 本プロジェクトの第三者ライセンス・NOTICE文書の追加・更新・削除要否が判断されているか。
- 必要なライセンス全文とNOTICEが原文のまま収録され、ビルド成果物から利用者が到達できるか。
- ライセンス不明、条件競合、遵守できない依存を見落としていないか。

## 指摘方法

- 重要度の高い問題から報告する。
- 対象ファイル・箇所・問題理由・発生条件・影響を示す。
- 修正案は必要最小限にする。
- 単なる好みや無関係なリファクタリングは指摘しない。
- 問題がなければ確認した観点を明示する。
