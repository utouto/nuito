# ドキュメント管理

仕様、設計、運用情報を実装と一致させるための手順です。

## 原則

- docsは本プロジェクト固有の仕様・設計・意思決定の正本として扱う。
- Skillには作業方法、Agentには担当責務、docsには現在の状態を記載する。
- 同じ情報を複数文書へコピーしない。
- 古い文書を放置したまま代替文書を増やさない。
- コードから自明な実装詳細を過剰に文書化しない。

## 更新判断

次の変更ではdocs更新の必要性を確認する。

- 利用者向け仕様、API、DB、アーキテクチャ
- AI処理、外部サービス、外部データソース
- 開発環境、環境変数、必要ツール
- テスト、CI/CD、デプロイ、障害対応
- ライセンス、帰属表示、データ利用条件
- プロダクトの範囲、成功指標、要求の受け入れ条件
- 重要なアーキテクチャ判断と、それを置き換える判断

## 文書作成

- 目的と対象読者を冒頭で明確にする。
- 現在の仕様、将来案、未実装事項を区別する。
- ファイルパス、コマンド、設定名が実在することを確認する。
- 外部仕様は可能な限り公式の一次情報を参照する。
- 外部データを配布・加工する場合は、提供者、URL、ライセンス、加工内容、基準日、更新方法を記録する。

配置は既存構成を優先する。新規プロジェクトでは、必要に応じて `docs/product/`、`docs/management/`、`docs/architecture/`、`docs/database/`、`docs/api/`、`docs/ai/`、`docs/development/`、`docs/operations/` などへ責務を分ける。

重要な技術判断は `docs/architecture/decisions/` のADRとして記録する。採用済みADRを後から都合よく書き換えず、新しい判断から置換関係を示す。

## 完了時

- 実装、設定、テスト、docsの一致を確認する。
- リンク切れ、重複、陳腐化した記述を確認する。
- 更新不要と判断した重要領域があれば理由を説明する。
