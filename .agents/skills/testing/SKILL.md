# テスト

振る舞いを検証するテストを設計・実装・実行するための手順です。

## 開始前

1. `AGENTS.md` と関連する `docs/` を確認する。
2. [`docs/development/testing-strategy.md`](../../../docs/development/testing-strategy.md) が存在する場合は、テストレベル、対象リスク、環境境界、現在の実行方法を確認する。
3. 既存のテストフレームワーク、配置、命名、ヘルパーを調べる。
4. 対象機能の公開された振る舞いと完了条件を整理する。
5. 既存テストで同種のパターンがないか確認する。

## テストレベルを選ぶ

変更内容に応じて、次のうち必要なレベルを選ぶ。名称だけで判断せず、結合する範囲を基準にする。

- UT: 外部境界やUIから切り離せる関数・ロジックを単独で検証する。
- IT: コンポーネント間、UIと状態、サービスとDBなど、複数の責務の連携を検証する。
- ST: ビルドしたアプリを利用者と同じ入口から操作し、重要な導線を検証する。

すべての変更へ3レベルを機械的に追加しない。低いレベルで十分に保証できるものはUTまたはITへ置き、STは主要導線と環境依存の振る舞いに絞る。

テストファイルの配置とコマンドは、本プロジェクトの設定、既存テスト、テスト方針docsを正本とする。

## テスト観点

最低限、必要性を判断する。

- 正常系
- 異常系
- 境界値
- 空値、NULL、未定義
- 不正入力
- 権限・認証
- 外部サービス失敗
- DB失敗
- 非同期処理
- 複数の非同期取得が同じ画面状態へ反映される場合の応答順逆転、キャンセル、古い応答による上書き
- 重複実行
- 回帰
- 時刻や順序に依存する処理

すべてを機械的に追加せず、仕様上意味のあるケースを選ぶ。

## テスト実装

- 可能な限り外部から観測できる振る舞いを検証する。
- 実装詳細への過剰な依存を避ける。
- 実装コードと同じロジックをテスト側に再実装しない。
- assertionは期待する結果を具体的に検証する。
- 過剰なmockを避ける。
- 外部API、時刻、乱数などは必要な境界で制御する。
- テスト同士を実行順序に依存させない。

## バグ修正

可能なら、修正前に失敗する再現テストを追加する。
修正後、そのテストが成功することを確認する。

## 実行

1. 変更したテストを実行する。
2. 関連するテストスイートを実行する。
3. 必要なら全体テストを実行する。
4. 失敗時は「テストの問題」と「本番コードの問題」を切り分ける。

## 完了条件

- 重要な振る舞いが検証されている。
- テストが意味のあるassertionを持つ。
- flakyになりやすい依存を制御している。
- 実行したコマンドと結果を報告できる。
- 追加または省略したテストレベルの理由を説明できる。
- 必要に応じて `test-review` Skillのインスペクションを実施または依頼している。
