# 可観測性

障害や劣化を安全に検知・調査できるよう、必要十分な観測情報を設計するための手順です。

## 開始前

1. `AGENTS.md` と、存在する場合は運用・障害対応docsを確認する。
2. 対象処理、利用者影響、信頼境界、既存のログ・metrics・traceを確認する。
3. 誰が、どの状況で、何を判断するための観測情報かを定義する。
4. 保存期間、閲覧権限、利用コストを確認する。

## ログ

- 調査に必要なevent、結果、相関ID、処理時間を構造化して記録する。
- APIキー、token、password、session、個人情報、入力本文を安易に記録しない。
- エラーを握りつぶさず、同じ失敗を複数層で重複記録しない。
- log levelを一貫させ、正常処理をerrorとして記録しない。
- 高頻度処理で無制限にログ量が増えないよう確認する。

## metrics・trace

- 利用者影響を示す成功率、失敗率、latency、処理量、queue滞留などから必要なものを選ぶ。
- labelやdimensionのcardinalityを制御する。
- 分散処理では相関可能なtrace・request IDを境界で伝播する。
- instrumentation自体のCPU、通信量、保存コストを確認する。

## alert・health check

- 対応可能な事象だけをalertにする。
- 単発ノイズと継続障害を区別し、重複通知を抑える。
- 閾値、評価期間、通知先、担当、初動手順を明確にする。
- health checkは依存先を過剰に連鎖させず、用途に応じて生存確認と準備完了を分ける。

## 検証

- 正常系と代表的な失敗を発生させ、期待する観測情報を確認する。
- 機微情報が出力されないことを確認する。
- alertのテスト方法と、通知を発生させずに検証する方法を確認する。
- 観測基盤が停止しても、主要処理を不必要に停止させない設計か確認する。

## 境界

- 性能測定と最適化は `performance-audit` を併用する。
- ログ内の機微情報や監視画面の権限は `security-review` を併用する。
- 外部監視サービスや依存追加は `dependency-management` を併用する。

## 完了時

- 追加したsignal、利用目的、保存期間、閲覧範囲、費用への影響を説明する。
- dashboard、alert、runbookなど関連docsの更新要否を確認する。
