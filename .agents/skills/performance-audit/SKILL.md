# 性能監査

性能問題を計測と根拠に基づいて評価するための標準手順です。

## 原則

- 計測せずに最適化を決めない。
- 再現条件、データ量、同時実行数、環境を明示する。
- 現在のボトルネックと将来のスケールリスクを区別する。
- レイテンシだけでなくCPU、メモリ、DB、ネットワーク、外部API、コストを評価する。
- 改善後は可能な限り同じ条件で再計測する。

## 手順

1. [`docs/product/product-brief.md`](../../../docs/product/product-brief.md) が存在する場合は、想定規模、重要操作、性能目標、コスト管理方法、計測環境を確認する。目標がなければ勝手にSLOを決めない。
2. 変更前または現状のベースラインを取得する。
3. profiler、trace、query plan、network記録などで主要因を特定する。
4. 期待効果、実装コスト、複雑性、正しさへのリスクを比較する。
5. 最小の改善を行い、同条件で再計測する。

## 確認観点

- 初期読込量、不要な再描画・再計算、過大な静的アセット
- APIの重複呼び出し、過大なresponse、pagination、timeout、retry
- DBの全件走査、N+1、インデックス不足、transaction範囲
- 大量データの一括展開、巨大な中間配列、解放されないlistenerやtimer
- serialな外部呼び出し、無制限の並列処理、不要なデータ変換
- cacheの効果と陳腐化・整合性・無制限増加のリスク
- AIや外部APIの呼び出し回数、入力サイズ、batch可能性、利用コスト
- データ量や同時利用者数が増えたときの計算量と資源使用量

改善は、不要処理の除去、取得・処理量の削減、適切なquery、重複排除を優先し、その後にcache、batch、lazy loadingなどを検討する。

## 完了時の出力

1. 監査対象と再現条件
2. ベースライン
3. 問題と根拠
4. 重要度と発生条件
5. 改善候補とトレードオフ
6. 再計測結果または再計測方法

計測できない項目は、静的なリスク分析であることを明示する。
