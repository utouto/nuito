# アクセシビリティレビュー

利用者が入力方法、視覚、聴覚、認知特性にかかわらず主要機能を利用できるか確認するための手順です。

## 準備

1. `AGENTS.md`、対象画面の仕様、[`docs/product/product-brief.md`](../../../docs/product/product-brief.md) に記録された対象platform・アクセシビリティ基準・対象browser・支援技術を確認する。
2. 主要導線、対象platform、browser、支援技術を確認する。
3. 変更差分だけでなく、関連コンポーネントと実際の表示を確認する。
4. 自動検査だけで完了とせず、必要な手動操作を整理する。

## 確認観点

### 構造・名前

- 見出し、landmark、list、table、formが意味に合う要素で構成されているか。
- 操作要素に認識可能な名前、label、説明があるか。
- ARIAをネイティブ要素の代替として不必要に使っていないか。
- 状態やエラーが視覚表現だけでなく支援技術にも伝わるか。

### keyboard・focus

- 主要機能をkeyboardだけで操作できるか。
- focus順が理解可能で、focus表示が見えるか。
- dialog、menuなどでfocus移動・復帰・Escape操作が適切か。
- keyboard trapや、hoverだけで利用できる機能がないか。

### 視覚・表示

- 情報を色だけで区別していないか。
- 文字、UI部品、focus表示に必要なcontrastがあるか。
- zoom、文字拡大、狭いviewportで内容や操作が失われないか。
- animationや点滅が利用者設定を尊重し、操作を妨げないか。

### 入力・feedback

- 入力目的、必須条件、形式、エラー箇所、修正方法が分かるか。
- timeoutや自動更新に対して利用者が制御・延長できるか。
- 非同期更新や通知が適切に伝わり、focusを予期せず奪わないか。

### media・非テキストコンテンツ

- 意味のある画像に適切な代替テキストがあるか。
- 装飾画像を支援技術へ不要に読ませていないか。
- 音声・動画に、用途に応じた字幕、transcript、操作手段があるか。

## 検証

- keyboardだけで主要導線を操作する。
- browserのアクセシビリティtreeと名前・role・stateを確認する。
- zoom、文字拡大、狭いviewport、配色設定を確認する。
- 自動検査が利用可能なら実行するが、検出できない問題を手動確認する。
- 実機やscreen readerを確認できない場合は未検証として明示する。

## 出力

- 重要度、対象箇所、影響を受ける操作、再現手順を示す。
- 適用する基準と、違反または利用上の障壁を区別して説明する。
- 最小限の修正案と、修正後の確認方法を示す。
- 単なるHTMLの好みや、利用上の影響が説明できない指摘を避ける。
