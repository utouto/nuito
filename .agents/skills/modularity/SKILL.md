# モジュール性と責務分割

行数だけに頼らず、変更理由と依存関係に基づいてコードを理解可能な単位へ分割するための手順です。

## 開始前

1. `AGENTS.md`、関連docs、`coding-standards` を確認する。
2. 対象ファイルの入口、利用者、データフロー、状態、外部境界を確認する。
3. 既存テストで現在の振る舞いを把握する。
4. 機能変更と構造変更を区別し、無関係な全面改修を避ける。

## 分割を検討する兆候

- 独立した複数の変更理由を持っている。
- UI、domain logic、データ取得、変換、永続化など異なる責務が混在する。
- 関数の理解に離れた場所のmutable stateを追う必要がある。
- 条件分岐、例外処理、状態遷移が重なり、主要経路が見えない。
- 一部のテストに無関係な依存や大規模なfixtureが必要になる。
- 変更のたびに広範囲へ影響し、merge conflictが繰り返される。
- public APIと内部実装の境界が不明確である。

ファイル行数、関数行数、引数数、nestの深さは調査開始のsignalとして使えるが、それだけを違反や分割理由にしない。generated code、宣言的設定、schema、fixtureなどは性質を考慮する。

## 境界の決め方

- 一緒に変更される処理とデータを近くに置く。
- domain上の概念、外部境界、状態の所有者など、説明できる責務名を付ける。
- orchestratorと個別処理、純粋な計算と副作用を分ける。
- 内部詳細を公開せず、必要最小限のAPIにする。
- 依存方向を一方向にし、循環依存を作らない。
- 抽出後に引数や共有状態が不自然に増える場合は、境界を再検討する。

## 避けること

- 行数を減らすだけの意味のないファイル分割。
- 1回しか使わない小処理の機械的な関数化。
- 無関係な処理を `utils`、`helpers`、`common` へ集約すること。
- interfaceやwrapperを将来予測だけで追加すること。
- module間でmutable stateを共有すること。
- 分割と同時に振る舞いやpublic APIを理由なく変更すること。

## 実施手順

1. 維持すべき外部の振る舞いと契約を固定する。
2. 分割候補ごとの責務、入力、出力、副作用、依存先を整理する。
3. 最小の境界から抽出し、呼び出し側を単純に保つ。
4. import graph、循環依存、public APIの増加を確認する。
5. 対応するテストを実行し、必要なら境界単位のテストを追加する。
6. 分割前後の差分を確認し、単なる移動に機能変更が混ざっていないか確認する。

## 完了条件

- 各module・関数の責務を短く説明できる。
- 依存方向と状態の所有者が明確である。
- 主要な呼び出し側が分割前より理解しやすい。
- 過剰な委譲、引数、公開API、循環依存を増やしていない。
- 振る舞いがテストで維持されている。
