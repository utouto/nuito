# リリース管理

リリース内容と公開条件を一貫して管理するための手順です。

## 開始前

1. `AGENTS.md` と、存在する場合はリリース・バージョニングdocsを確認する。
2. 対象バージョン、対象ブランチ、配布先、公開範囲を確認する。
3. 前回リリースとの差分と、利用者へ影響する変更を特定する。
4. breaking change、migration、設定変更、Secret追加の有無を確認する。
5. `docs/operations/operational-readiness.md` が存在し、対象プロジェクトに運用準備が必要な場合は確認する。

## バージョン

- リポジトリで採用済みのバージョニング方式に従う。
- バージョンを複数ファイルで管理している場合は同じ変更単位で同期する。
- 互換性を破壊する変更をpatch相当として扱わない。
- pre-releaseと正式版の用途を混同しない。

## リリースノート

- 利用者に意味のある変更を中心にまとめる。
- 追加、変更、修正、廃止、セキュリティ対応、既知の制約を区別する。
- migrationや手動設定が必要なら、順序と失敗時の復旧方法を示す。
- 内部実装の列挙や、確認できない効果の断定を避ける。
- Secretや非公開の脆弱性詳細を含めない。

## 公開前確認

- 作業ツリーとリリース対象差分を確認する。
- 本プロジェクトで定義されたlint、typecheck、test、buildを実行する。
- artifact、第三者ライセンス、設定例、docsの更新を確認する。
- 対象コミットが必要なremoteへ反映済みか確認する。
- 実行できない検証や既知の問題を明示する。
- health確認、監視、rollback、backup/restore、障害時のownerがリスクに応じて準備されているか確認する。

## 外部操作

- 明示的な依頼なしに公開、デプロイ、パッケージ配布を実行しない。
- AIエージェントは `git push` を実行しない。
- タグ作成はリポジトリ方針とユーザーの許可を確認する。許可がなければ、必要なタグと手動コマンドを案内する。
- CI/CDワークフロー自体の追加・変更は `ci-cd` Skillを使う。

## 完了時

- バージョン、対象コミット、変更概要、検証結果を報告する。
- migration、設定変更、rollback、未実施の手動操作を明示する。
- リリース後確認が必要なら、確認項目と期待結果を示す。
- プロダクト成功指標を確認するownerと時期が定義されているか確認する。
