# コーディング規約

本プロジェクト固有の規約を、既存コードと自動化設定に沿って一貫して適用するための手順です。

## 正本

1. `AGENTS.md` を確認する。
2. [`docs/development/coding-standards.md`](../../../docs/development/coding-standards.md) を確認する。
3. formatter、linter、compiler、既存コードの設定を確認する。
4. 記述が矛盾する場合は、勝手に解釈せず差異と影響を明示する。

本プロジェクトで規約docsの配置を変更した場合は、この参照も同期する。

## 適用

- 既存の命名、書式、import、型、エラー処理の慣習へ合わせる。
- formatterやlinterで表現できる規則は、文章だけに依存しない。
- lint抑制、型検査の無効化、広い例外指定で違反を隠さない。
- プロジェクト固有の規則またはユーザーの指定がない限り、新しく記述するコメントは日本語を基本とする。
- コメントは処理の逐語説明ではなく、理由、制約、非自明な判断を記録する。
- 識別子、API名、外部仕様の用語、generated code、vendor codeなど、日本語化が不適切な箇所は原表記または必要な形式を優先する。
- publicな境界では入力、出力、失敗方法を明確にする。
- 新しい規約は、継続的に適用でき、実際の不具合や理解コストを減らす場合だけ追加する。

## 変更時

- 規約変更が既存コードへ与える影響を確認する。
- 大量の機械的変更と機能変更を同じ差分へ混在させない。
- 新しいtoolや依存が必要なら `development-environment` と `dependency-management` を使う。
- CIへ検査を追加・変更する場合は `ci-cd` を使う。
- 責務やファイル構造の見直しには `modularity` を使う。

## 検証

- 本プロジェクトに存在するformatter、lint、typecheck、testを実行する。
- 自動検査できない規則は差分レビューで確認する。
- generated code、vendor code、migrationなどの例外が意図的か確認する。
- 実行できない検証と手動確認項目を明示する。

## 完了時

- 適用した規約と例外を説明する。
- 規約docs、tool設定、実装が一致していることを確認する。
