# 依存関係管理

外部パッケージの追加・更新・削除を必要最小限かつ再現可能に行うための手順です。

## 追加前

次を順に確認する。

1. 標準機能で実現できないか。
2. 既存依存で実現できないか。
3. 小さな自前実装の方が保守しやすくないか。
4. パッケージ導入の価値が十分にあるか。

## 調査

追加・更新する場合は可能な範囲で確認する。

- 公式・一次情報
- 現在のメンテナンス状況
- ライセンス
- Node.js等の必要バージョン
- ESM / CJS互換性
- 対象runtime・実行環境との互換性
- TypeScript型
- bundle sizeへの影響
- 既知のセキュリティ問題
- transitive dependencies

## 変更

- 本プロジェクトで採用済みのpackage managerを使う。
- lockfileを正規のinstallコマンドで更新する。
- lockfileを手編集しない。
- 無関係なパッケージを同時更新しない。
- major updateは破壊的変更を確認する。
- deprecated APIの移行を確認する。

## ライセンスと第三者表記

依存パッケージを追加、更新、削除した場合は、コミット前に直接依存と新たに増減したtransitive dependencyのライセンスを確認する。パッケージ名や記憶だけで判断せず、インストールされたpackage metadata、同梱された `LICENSE`、`NOTICE`、公式リポジトリなどの一次情報を確認する。

最低限、次を確認する。

- 商用利用、改変、再配布、SaaSやクライアント配信など本プロジェクトの用途で許可されるか
- 著作権表示、ライセンス全文、NOTICE、ソース提供、改変表示などの条件があるか
- runtime dependencyとして配布・実行されるか、開発時だけ利用されるか
- copyleft、複数ライセンス、独自ライセンス、ライセンス不明の依存が含まれないか
- 既存のライセンスや本プロジェクトの配布方法と矛盾しないか

本番で配布または実行する依存に表示・同梱義務がある場合は、本プロジェクトの第三者ライセンス・NOTICE文書を同じ変更単位で更新する。ライセンス本文やNOTICEは要約で置き換えず、配布元の原文を保持する。依存を削除した場合は、その依存だけが必要としていた表記を残さない。

ビルド後は、必要なライセンス文書が成果物へ含まれ、原本と一致することを確認する。利用条件が不明、競合、または本プロジェクトで遵守できない場合は、依存の採用を止めてユーザーへ報告する。

## 削除

- importだけでなく設定、script、docs、型、CIからの参照も確認する。
- 削除後に不要なtransitive設定を残さない。

## 検証

変更後、利用可能な範囲で実行する。

- install
- lint
- typecheck
- test
- build

## 完了時

- なぜ追加・更新・削除したか説明する。
- 互換性上の注意があれば明示する。
- 追加・更新・削除した依存のライセンス確認結果を説明する。
- 必要な第三者ライセンス・NOTICE表記とビルド成果物が依存状態に一致している。
- 開発手順が変わる場合はdocsを更新する。
