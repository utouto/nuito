- 適用判断: Cloudflare staging・production作成前に適用する。初回公開手順は `cloudflare-production-release.md` を正本とする。

- migrationの有無、順序、互換性: `migrations/` を番号順に適用する。まずstagingへ適用し、互換性確認後にproductionへ適用する。
- health確認とリリース後の主要signal: `GET /api/health`。本文、画像、座標、利用者IDをログへ出さない。
- rollbackまたは前進修正の条件と手順: Workerは直前deploymentへrollbackする。D1 migrationは破壊的変更を避け、原則として前進修正する。

適用しない項目も空欄にせず、対象外と判断した理由を記載します。外部公開や永続データがあるのに、担当や復旧方法が未決定の状態を「対象外」として扱いません。

## 所有と連絡

- [ ] 運用責任者と障害時の連絡方法が決まっている
- [ ] 障害の重要度と、判断・連絡・復旧の責任が決まっている
- [ ] 外部サービスのstatus、support、利用制限を確認できる

## 可観測性

- [ ] 利用者影響を示すSLIと、必要な場合はSLOを定めた
- [ ] log、metrics、traceの目的、保存期間、閲覧権限を定めた
- [ ] 対応可能なalertだけを設定し、初動runbookへ接続した
- [ ] Secretや個人情報が観測データへ出ないことを確認した

## リリースと復旧

- [ ] health/readinessの確認方法がある
- [ ] migrationの順序、互換性、失敗時の復旧方法がある
- [ ] rollbackまたは安全に前進修正する条件と手順がある
- [ ] リリース後に確認するsignalと担当者が決まっている

## データ

- [ ] データ分類、保存場所、権限、保持期間、削除方法を定めた
- [ ] backupが必要なデータと復旧目標を定めた
- [ ] restoreを実際に検証する方法と頻度を定めた
- [ ] 利用者からの開示・訂正・削除要求への対応を確認した

## 障害後

- [ ] 利用者影響、時系列、原因、復旧、再発防止を記録する
- [ ] 個人の責任追及ではなく、仕組みと防御の改善へつなげる
- [ ] follow-upをownerと期限のあるIssueとして追跡する
