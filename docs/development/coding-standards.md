# コーディング規約

この文書は、本プロジェクトでコードの一貫性と保守性を保つための規約の正本です。採用言語、framework、toolが決まったら、既存設定と一致するよう具体化してください。

## 優先順位

規則が競合する場合は、原則として次の順で判断します。

1. 正しさ、セキュリティ、利用者との契約
2. formatter、linter、compilerなど実行可能な設定
3. この文書に記載されたプロジェクト規約
4. 周辺コードで一貫して使われている慣習
5. 個人の好み

矛盾が見つかった場合は、局所的な例外を増やす前に設定または本文を修正します。

## 基本原則

- 読み手が処理の目的、主要経路、失敗方法を追えるコードを書く。
- 変更に必要な範囲だけを編集し、無関係な整形やリファクタリングを混在させない。
- 同じ知識や判定を複数箇所へ重複させない。
- 将来の可能性だけを理由に抽象化、設定項目、拡張ポイントを追加しない。
- lint、型検査、テストの無効化で問題を隠さない。

## 命名

- 名前から責務、単位、真偽、所有関係が理解できるようにする。
- 略語はdomainで一般的なものに限定し、同じ概念へ異なる名前を使わない。
- booleanには状態または判定だと分かる名前を使う。
- `data`、`info`、`item`、`value`、`temp` のような曖昧な名前は、狭いscopeで意味が明白な場合に限る。
- ファイル・ディレクトリ名は主要な責務またはdomain概念を表す。

## 関数と処理

- 関数は1つのまとまりある目的を持ち、名前と実装を一致させる。
- 正常経路を追いやすくし、必要に応じてguard clauseで異常条件を先に扱う。
- 引数、戻り値、副作用、失敗方法を明確にする。
- boolean引数が呼び出し側で意味不明になる場合は、名前付きoptionや責務分割を検討する。
- 同じ引数群が繰り返される場合は、意味のあるデータ構造か責務境界が不足していないか確認する。

## モジュールとファイル

- 1ファイルへ異なる変更理由を持つ責務を集めない。
- UI、domain logic、I/O、永続化、外部サービス境界を、採用アーキテクチャに沿って分離する。
- 一緒に変更される処理とデータは近くに置く。
- `utils` や `helpers` を無関係な処理の置き場にしない。
- 行数は絶対的な上限にせず、責務過多を調査するsignalとして扱う。
- 詳細な判断と手順は `modularity` Skillに従う。

## 型とデータ

- 型で表現できる不変条件は型またはvalidationで表現する。
- 型検査を回避する広すぎる型や強制変換を安易に使わない。
- 外部入力は信頼せず、system境界で検証する。
- `null`、未定義、空値の意味を区別し、契約として一貫させる。
- 日時、timezone、金額、単位、識別子を曖昧なprimitiveとして扱う場合のリスクを確認する。

## エラー処理

- エラーを握りつぶさず、回復、変換、通知、再送出のどれを行うか明確にする。
- 利用者向けエラーと内部診断情報を分離する。
- Secret、個人情報、内部構造をエラーやログへ露出しない。
- retryは冪等性、上限、backoff、重複実行への影響を確認する。

## コメントとドキュメント

- プロジェクト固有の規則がない限り、新しく記述するソースコード内のコメントは日本語を基本とする。
- コードから明白な処理をコメントで逐語的に繰り返さない。
- 理由、制約、trade-off、外部仕様、直感に反する判断を記録する。
- 識別子、API名、規格名、引用するエラーメッセージなどは原表記を保ち、不自然に翻訳しない。
- generated code、vendor code、外部projectの規約、言語・frameworkの標準形式が別の言語を要求する場合は、その形式を優先する。
- TODOには必要に応じて条件、理由、追跡先を含める。
- public APIのdocument方法は、採用言語・frameworkの慣習へ合わせる。

## 見直し

- 規約は実際に繰り返される問題を防ぐために追加する。
- 守られない規則は、必要性、自動化可能性、表現の明確さを見直す。
- 規約変更による大量の機械的差分は、機能変更と分離する。
