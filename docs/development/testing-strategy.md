# テスト戦略

この文書は、本プロジェクトで重要な振る舞いをどのテストレベルと環境で保証するかの正本です。プロジェクト開始時に具体化し、対象外のレベルや境界には理由を記載します。個々のテストケースやテスト実装手順は重複して記載しません。

## 対象リスク

- 主要なリスク: 論理日付、時刻不明投稿の順序、日記案内期間、画像・IndexedDB保存。
- 主要な利用者導線: 利用開始、ぬい登録、投稿作成・編集、日別日記、設定変更、削除。
- 回帰時の影響が大きい契約・境界: 日時算出と投稿sort、IndexedDB schema、画像処理、ブラウザ位置情報。

## テストレベルの責務

- UTの責務: `src/domain.test.ts` で時刻・日付・順序の規則を検証する。
- ITの責務: Worker handlerのD1・R2到達性、認証前の拒否、障害responseをmock境界で検証する。UIとIndexedDBの連携は今後追加し、現版では手動確認を併用する。
- STの責務: 対象スマートフォン実機で主要導線、写真、位置情報、容量不足をリリース前に確認する。

すべての振る舞いを複数レベルで重複検証せず、最小の適切な結合範囲で保証します。採用しないテストレベルには、対象外とする理由を記載します。

- 実環境境界:
- DB・queue・filesystemの扱い:
- 外部API・外部サービスの扱い:

mockやstubは外部境界など必要な箇所に限定し、重要な連携を分断しないようにします。本番データやSecretをテストへコピーしません。

## 安定性と保守

- flaky testの扱い:
- 時刻、乱数、非同期処理の制御: domain関数へ日時を引数で渡し、UTでは固定日時を使用する。
- 失敗時の診断情報とtest report:
- test suiteを見直す条件と担当:

再試行や無効化で恒常的な失敗を隠しません。flaky testはownerと期限のあるIssueで追跡し、修正または隔離の判断理由を記録します。
