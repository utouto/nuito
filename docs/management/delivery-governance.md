# 開発・変更管理

この文書は、要求からリリースまでの判断基準を定めます。プロジェクト開始時に、実際の担当、branch protection、承認条件へ更新してください。

## 役割と所有

最低限、次の責任者を明確にします。同じ人が複数を担当しても構いません。

- プロダクト判断の担当:
- 要求の正本と優先順位の決定方法:
- 技術判断の担当:
- セキュリティ窓口の担当:
- 運用責任の担当:
- 必須レビュー人数:
- branch protectionまたはrulesetの確認担当と確認方法:
- リリース責任者:
- 定期見直しの担当と頻度:

各担当の責務は次のとおりです。

- プロダクト判断: 優先順位、範囲、受け入れの最終判断
- 技術判断: アーキテクチャ、品質、技術的リスクの判断
- セキュリティ窓口: 非公開報告の受領と対応調整
- 運用責任: リリース、監視、障害、rollbackの判断

GitHubを使う場合は、実在するteamまたはuserで `CODEOWNERS` を作成し、重要領域のレビューを必須化します。テンプレートには架空のownerを登録しません。

要求の正本をIssue、project board、外部backlogなどから1つ定め、緊急度、利用者価値、リスク、依存関係を誰が判断して着手順へ反映するかを記録します。複数の管理場所を使う場合は、状態と優先順位の正本を明示します。

## Definition of Ready

実装開始前に、変更規模に応じて以下を満たします。

- 課題、対象利用者、期待する成果が説明できる
- 対象範囲と非対象が明確である
- 観測可能な受け入れ条件がある
- 不明点、依存関係、主要リスクが整理されている
- DB、API、外部サービス、セキュリティ、運用への影響を確認した
- 大きな設計判断はADRまたは設計文書で合意されている

探索作業では、成果物を「判断に必要な情報」として定義し、未確定の実装を約束しません。

## Definition of Done

- 受け入れ条件を満たしている
- 必要なテストがあり、定義済みの自動チェックが成功している
- 仕様、コード、テスト、docsが一致している
- セキュリティ、プライバシー、アクセシビリティ、性能への必要な確認を行った
- migration、設定変更、監視、rollback、利用者通知を必要に応じて準備した
- 作成者以外の必要なレビューと承認を得た
- 未実施検証、既知の制約、残存リスクが明示されている

## Pull Requestとマージ

- 変更は小さく、1つのまとまりある目的に限定する。
- default branchへの直接pushを禁止する。
- 必須CIと必要人数のレビューをbranch protectionまたはrulesetで強制する。
- 本テンプレートでは `template-validation` を必須チェックに設定する。派生プロジェクトでは、これに採用技術固有のチェックを追加する。
- CIの迂回、テスト無効化、自己承認だけでのマージを認めない。
- 緊急変更では理由、承認者、事後レビュー期限を記録する。

## リリース判断

リリース責任者は、対象commit、変更内容、検証結果、既知の問題、migration、監視方法、rollback方法を確認します。公開後は利用者影響と主要signalを確認し、結果を記録します。

## 定期的な見直し

定期的に、未解決リスク、依存関係更新、失敗したCI、flaky test、障害、利用者feedback、目標指標を確認します。規則を増やす場合は、実際に繰り返される問題との対応を説明できるようにします。
