# 06. 非機能要件

## 1. 操作性

| ID | 優先度 | 要件 |
|---|---|---|
| NFR-001 | Must | スマートフォンでの片手操作を考慮する |
| NFR-002 | Must | 主要画面から2操作以内で投稿作成を開始できるようにする |
| NFR-003 | Must | 写真処理中、地図読込中、保存中は進行状態を表示する |
| NFR-004 | Must | 日付、時刻、時刻不明の違いが分かりやすいUIとする |
| NFR-005 | Should | 入力途中で誤って画面を閉じた場合のデータ消失を抑止する |
| NFR-006 | Must | エラー時に、原因と次の操作を文章で示す |

## 2. レスポンシブ対応

| ID | 優先度 | 要件 |
|---|---|---|
| NFR-010 | Must | 幅320px程度の画面から横スクロールなしで主要機能を利用できることを目標とする |
| NFR-011 | Must | iPhoneとAndroidスマートフォンを主要対象とする |
| NFR-012 | Should | PCでも投稿、閲覧、編集を利用可能とする |
| NFR-013 | Must | タップ対象には十分な大きさと間隔を設ける |
| NFR-014 | Should | ホーム画面追加時にアプリ風の表示を提供する |

## 3. 性能

| ID | 優先度 | 要件 |
|---|---|---|
| NFR-020 | Must | 保存済み投稿一覧と日別ページを、通常利用で大きな待ち時間なく表示する |
| NFR-021 | Must | 画像リサイズ・圧縮中に画面全体を無反応にしない |
| NFR-022 | Must | 画像が多い日でも、サムネイルを使って表示負荷を抑える |
| NFR-023 | Must | 地図には対象日分のピンと線のみを描画する |
| NFR-024 | 暫定 | 詳細な性能目標値は、対象端末と地図サービス決定後に定める |

## 4. セキュリティ

| ID | 優先度 | 要件 |
|---|---|---|
| NFR-030 | Must | HTTPSで提供する |
| NFR-031 | Must | 位置情報とカメラ権限は、必要な操作時にのみ要求する |
| NFR-032 | Must | ユーザー入力を検証し、不正なスクリプト等が実行されないようにする |
| NFR-033 | Must | 外部地図サービスへ、日記本文やぬいぐるみ情報を不要に送信しない |
| NFR-034 | Must | 全データ削除等の重大操作には確認手順を設ける |
| NFR-035 | Should | 依存ライブラリの更新と脆弱性確認を継続できる構成にする |

## 5. プライバシー

| ID | 優先度 | 要件 |
|---|---|---|
| NFR-040 | Must | 地図、位置情報、日記、写真を他ユーザーへ公開しない |
| NFR-041 | Must | 公開プロフィールを設けない |
| NFR-042 | Must | 地図の公開URLを発行しない |
| NFR-043 | Must | アクセス解析を導入する場合、日記本文、画像、正確な位置情報を収集しない |
| NFR-044 | Should | 外部向け画像を将来生成する場合、不要な位置情報メタデータを除去する |
| NFR-045 | Must | ローカル保存の性質とデータ消失リスクを説明する |

## 6. 信頼性・データ整合性

| ID | 優先度 | 要件 |
|---|---|---|
| NFR-050 | Must | 投稿本文、画像、ぬいぐるみ関連、場所等を可能な範囲で一貫して保存する |
| NFR-051 | Must | 一部だけ保存された不完全な投稿を作らない |
| NFR-052 | Must | 保存失敗時には、原因と再試行方法を案内する |
| NFR-053 | Must | 保存失敗時に既存データを破損させない |
| NFR-054 | Should | バックアップ復元前に整合性を検証する |
| NFR-055 | Should | データ形式の移行失敗時に、元データを保持する |

## 7. オフライン

| ID | 優先度 | 要件 |
|---|---|---|
| NFR-060 | Must | 保存済みの投稿、ぬいぐるみ、日記本文を可能な範囲でオフライン閲覧・編集できる |
| NFR-061 | Must | 地図背景、施設検索、住所検索はオンライン利用を基本とする |
| NFR-062 | Must | オフライン中に地図を利用できない場合、その旨を表示する |
| NFR-063 | Must | オフライン中の編集内容を端末内へ保存できる |
| NFR-064 | Should | アプリシェルをキャッシュし、再訪時に基本画面を開けるようにする |

## 8. アクセシビリティ

| ID | 優先度 | 要件 |
|---|---|---|
| NFR-070 | Must | 入力欄とボタンに読み上げ可能な名称を付ける |
| NFR-071 | Must | 色だけに依存して状態を表現しない |
| NFR-072 | Must | 日本語本文は端末標準の丸みのあるゴシック体を優先し、本文と入力欄は16px相当、補足文字は原則12px以上、主要タップ領域は44px以上を確保する。見出しは同系統の書体と大きさ・太さで本文との差を示す |
| NFR-073 | Must | エラーは色に加えて文章で説明する |
| NFR-074 | Should | キーボード操作とフォーカス移動を考慮する |
| NFR-075 | Should | 動きの軽減設定を尊重する |

## 9. 保守性

| ID | 優先度 | 要件 |
|---|---|---|
| NFR-080 | Must | 保存データにデータ形式のバージョン情報を持たせる |
| NFR-081 | Must | LINEログインと、将来のクラウド同期・バックアップ復元を考慮したデータ構造とする |
| NFR-082 | Must | 一日の切り替え時刻、日記案内時刻、画像設定を固定値ではなく設定値として管理する |
| NFR-083 | Should | ドメインロジックを画面表示から分離し、テスト可能にする |
| NFR-084 | Should | 要件IDとテストケースの対応を維持する |

## 10. ブラウザ・端末対応

- 対応ブラウザの具体的なバージョン範囲は、基本設計時に決定する。
- 少なくとも、対象時点で一般利用されるiPhone SafariとAndroid Chromeで主要フローを検証する。
- カメラ、画像形式、位置情報、ストレージ容量の差異を実機で確認する。
- 未対応機能がある場合も、投稿本文や既存記録の閲覧を可能な範囲で維持する。
